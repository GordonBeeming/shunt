# shunt command reference

The CLI is `shunt-dev` (dev channel). Release/beta builds are `shunt`/`shunt-beta` — same commands.

| Command | What it does |
|---|---|
| `shunt-dev active [--json]` | Is the current dir a shunt app? Lists sidings with `live`, `appRunning`, `guestRunning`, and the `src` edit path. Exits non-zero (plain mode) when it's not a shunt app. |
| `shunt-dev ls [-a] [--json]` | Sidings for the **current project**, with a `STATUS` column: `live` (front door points here), `up` (running + bridged, ready to `switch` to), `idle` (exists but not ready), or `stopped` (killed); the `host` row shows `-` when it isn't live. `-a`/`--all` lists every project on the host. `--json` for tooling. |
| `shunt-dev status [--fix] [--json]` | Health of the channel's machinery (Caddy admin, both LaunchAgents, container runtime) + per-app front-door drift — a live route whose Caddy dial no longer matches the live siding's current guest IP (happens when a guest restarts and gets a new IP). `--fix` re-points the drifted app. |
| `shunt-dev new <name>` | Create a siding: assure the exact content-versioned base image locally with Apple `container`, then create a git worktree, data cloned from the selected baseline generation (or an empty initial source), and an idle guest. It never asks a registry for a missing Shunt base tag. Lifecycle commands compare the selected image-cache generation with the guest marker, load only missing or changed refs, then update the marker. It does not start the application. With no start flag, ordinary repos use the current HEAD. If HEAD is a GitButler internal workspace ref, shunt uses `origin`'s configured default branch so the siding isn't attached to GitButler's mutable workspace commit. `--branch <ref>` explicitly chooses the start point for a new siding branch; `--from <branch>` fetches and continues an existing remote branch. |
| `shunt-dev up <name>` | Assure the selected tag-only `prebakeImages` generation, compare it with the guest marker, Docker-load only missing or changed refs, and update the marker before inspecting every declared tag and starting the application. A siding never pulls live: an undeclared image, unavailable export, failed load, or failed inspection blocks startup. Then bridge the siding without moving the front door unless `--switch` is supplied. `--no-bridge` keeps all host routes untouched. |
| `shunt-dev warm [--from <siding>]` | Refresh every configured `prebakeImages` registry tag and rebuild every `prebakeBuilds` image, then atomically publish immutable per-image cache generations. `--from <siding>` captures a running guest's Docker store instead, bounded by the configured cache budget. A failed automatic collection warns without undoing the published generation. |
| `shunt-dev warm gc [--dry-run] [--max-bytes N]` | Run the collector that also follows every successful cache publication. It mark/sweeps unreachable generations, exports, and blobs. Current, previous, and actively leased generations are protected. The default budget is 100 GiB; protected data is never removed merely to meet it. Set `SHUNT_CACHE_MAX_BYTES` to change the default budget. |
| `shunt-dev data promote [siding] [-f]` | Promote the siding's complete declared-volume set. Source resolution is an explicit arg, cwd siding, live siding, then picker. The application and volume consumers are stopped and verified, data is durably committed, and the previous idle/running/live state is restored. A post-commit cleanup problem is printed as a warning and must not be retried as though publication failed. |
| `shunt-dev data rollback [-f]` | Durably swap the current and immediately previous complete data baseline. A post-commit cleanup problem warns without turning the already-completed mutation into a retryable failure. |
| `shunt-dev restart [name\|host]` | For a **siding**: compare the selected image-cache generation with the guest marker, Docker-load only missing or changed refs, update the marker, then kill only the app process and rebuild it, keeping the guest + dockerd + dependency containers + data running (use when hot reload misses a change). `restart host` is different — it (re)starts your **local** app natively, no guest involved; this is how you bring the host up after `switch host`, since `switch` only repoints and `restart`/`up` do the build + start. |
| `shunt-dev logs <name> [-n N]` | Print the siding's app log (build + startup + crash output) from inside the guest. Use to diagnose a failed `up`. |
| `shunt-dev git [args]` | Run **any** git command in the siding's worktree on the **host** (git doesn't resolve inside the guest). Args pass straight through to `git -C <worktree> <args>`; signs with your usual key, acts on the siding's `shunt/<name>` branch. Beyond `commit`/`push` this is the full surface for resolving a `sync` conflict — `status`, `diff`, `add`, `restore`, `rebase --continue`/`--abort`, `merge --abort`. Siding taken from cwd or the live one. |
| `shunt-dev sync [name] [--all] [--rebase] [--from <branch>]` | Pull the latest **default branch** (main, auto-detected from `origin/HEAD`) into a siding: `fetch origin` then **merge** it into the siding's `shunt/<name>` branch — a merge that picks up the latest code **without rewriting history** (fast-forwards when the siding has no local commits, else a merge commit; the safe default). `--rebase` rebases onto it instead (rewrites the branch — `git push --force-with-lease` after); `--all` syncs every siding (continues past conflicts, prints a summary); `--from <branch>` syncs from a branch other than the default. On conflicts it stops and lists the files — resolve them in the worktree with `shunt-dev git add …` + `shunt-dev git commit` (merge) or `shunt-dev git rebase --continue` (`--rebase`). Siding taken from the name arg, else cwd, else the live one. |
| `shunt-dev run [siding] [command...]` | Run a command inside a siding's guest, from the app's workdir (/workspace or the contract `workdir`), stdio passed through. No command drops into a shell. Which siding: the one your cwd is inside, else a leading arg that names a siding, else the live siding. For migrations, one-off dotnet/npm commands, etc. The guest-side complement to `shunt git`. |
| `shunt-dev playwright [siding] [args...]` | Execs `playwright-cli <args>` in a siding's running guest, from /workspace (or the contract `workdir`), stdio passed through — every arg goes straight to `playwright-cli` (no flags of its own beyond `-h`). Siding resolution matches `run`: the one your cwd is inside, else a leading arg naming a siding, else the live siding. The guest's app URLs are its own `https://localhost:<port>`, the same ones the app serves inside that siding — not a host-forwarded port. The image's global playwright-cli config pins the browser (chromium, sandbox off), so a bare `playwright-cli open <url>` needs no `--browser` flag. The browser session persists across invocations (the guest is long-lived); auto-named output (snapshots, traces, video saved without `--filename`) lands under `/out/playwright` in the guest, `<siding>/out/playwright` on the host — but only for sessions opened through this command; see Guest layout below. |
| `shunt-dev cd [name]` | Print a siding's **host worktree src** path to stdout so you can jump into it — a process can't cd its parent shell, so pair it with the shell: `cd "$(shunt-dev cd <name>)"` (or a function `scd() { cd "$(shunt-dev cd "$@")"; }`). Siding taken from the name arg, else cwd, else the live target; `host` (explicit, or when it's the live target) prints the original repo checkout instead of a siding. |
| `shunt-dev switch [name\|host]` | Point the stable front-door ports at a siding, or at `host` to serve the user's **local copy** natively. No name — arrow-key picker (host listed first). **Switch only repoints — it never starts or builds the app.** Switching to `host` just removes this app's Caddy front-door servers so the native app can bind the real ports (Caddy steps aside); the ports stay dead until you `restart host` or start something yourself (e.g. just the DB). Switching to a siding stops any running host app first (best-effort) and re-binds the front door — the siding shows dead ports until its app is `up`/`restart`ed. **Always confirm with the user before switching** — it repoints the shared front door and can interrupt another agent/session. |
| `shunt-dev dashboard [--install]` | Health-check and open the shunt web UI on this channel's localhost URL (dev `https://localhost:2220`, falling back to `http://localhost:2220` until the dev certificate and key exist). It is always-on via a LaunchAgent (`--install` to set it up or repair it; `init` does it too); an unhealthy loaded agent is restarted before the browser opens. Browse every app's front-door ports with live up/down status, switch between sidings, and **start/stop** each siding's guest — all with a click. Each siding shows a `running`/`idle`/`stopped` state (`running` only when the app is actually serving), its guest IP, and a dashboard link. Non-release channels show a corner ribbon. Switch + stop confirm first; start doesn't.|
| `shunt-dev up`/`restart`/`logs`/`kill`/`rm` `[name]` | All accept no name and fall back to the arrow-key picker (like `switch`). |
| `shunt-dev kill <name>` | Stop a siding's guest, keeping its worktree + data to restart later. If a graceful stop wedges on the guest's `cgroup.kill` (errno 95), `kill` force-removes the guest but keeps its worktree and data, then tells you to run `up` to recreate it. Any other stop failure is returned without removing the guest. |
| `shunt-dev rm <name> [-f\|--force]` | Tear down one siding: remove the guest, its worktree + branch, and its data. A dirty worktree is shown before removal and needs confirmation. A live siding is refused. `-f`/`--force` skips both checks. |
| `shunt-dev cleanup [-f\|--force]` | List the current project's sidings and select several to remove permanently. On a TTY, use ↑/↓, Space, and Enter; the non-TTY fallback accepts comma-separated numbers or `all`. Dirty worktrees are marked and need confirmation after selection. A live siding is refused. `-f`/`--force` skips the dirty-worktree check, confirmation, and live-siding refusal. An AI coding client must ask the user before confirming discarded changes or using force. |
| `shunt-dev reapply [name]` | Recreate a siding's guest from the app's **saved** settings (`memory`/`cpus`/`mounts`/`env`) while keeping its worktree, branch, and data clones. Lifecycle commands compare the selected image-cache generation with the guest marker, load only missing or changed refs, then update the marker. No name → the picker. Guest settings are baked in at creation, so an edit only reaches an existing siding via `reapply` then `up`. If you changed the root `.shunt.app.json`, run `app add` first — `reapply` reads saved state; only `app add` re-reads the contract. A siding's own `frontDoor` change applies on `up`/`switch`; don't run `app add` inside a siding because it repoints the app's `RepoPath` to that worktree. `--fresh-data` replaces the complete data set from the selected baseline generation, keeping the worktree and discarding that siding's data changes. |
| `shunt-dev app add` | Register the repo with shunt (reads `.shunt.app.json` from the **current directory** — run it in the **root repo**; it sets the app's `RepoPath`). Front-door ports are random+free by default (no collisions); `fixedPorts:true` pins them. Re-run to apply root-repo contract changes. A **siding's own** `.shunt.app.json` is read by `up`/`switch` on that siding instead — don't run `app add` from inside a siding (it would repoint `RepoPath` to the worktree). |
| `shunt-dev app switch <app>` | Make `<app>` active on its (fixed) front-door ports, parking any app that conflicts — without stopping the parked app's siding. For apps that share ports (e.g. Vite on the same port). |
| `shunt-dev init` | One-time machine setup: builds Caddy + the base image, starts the proxy. |
| `shunt-dev cert install` | Export the host's dotnet dev cert and load it into Caddy (front door serves HTTPS with the cert you already trust — no extra CA). |
| `shunt-dev config <branchPrefix|memory|cpus> [value]` | Get/set user-config defaults: `branchPrefix` (e.g. `gb/shunt/` — must end in `/` or `-`; it's joined straight onto the siding name, and only applies to sidings created after), `memory` (per-guest RAM, default `4g`), `cpus` (default `4`). A repo's `.shunt.app.json` `memory`/`cpus` overrides per app. Stored per channel in `<global-dir>/config.json`. Changing `memory`/`cpus` only reaches an existing siding after `shunt-dev reapply [siding]` + `up`. |

## Guest layout

- **`/out`** — every siding's guest gets a standing bind mount here, backed by `<siding>/out` on the host: outside the worktree and never committed, it's the landing spot for ad hoc logs or generated config you want to inspect from the host. `shunt-dev playwright` (above) auto-names its output under `/out/playwright` (`<siding>/out/playwright` on the host) via `PLAYWRIGHT_MCP_OUTPUT_DIR`, injected automatically; an explicit `--filename` bypasses that and resolves relative to the guest's cwd (the worktree) instead, so pass an explicit `/out/...` path if you want a named file to land there too. That env var is only set when the browser session **opens**, and the redirect it picks sticks for the session's whole life: a session opened via a manual `shunt-dev run <siding> playwright-cli open …` never gets it, so its auto-named output — video included — stays in the worktree's `.playwright-cli/` for as long as that session runs, even if later calls on it switch to `shunt-dev playwright`. Open sessions through `shunt-dev playwright`; treat `shunt-dev run … playwright-cli` as a fallback whose output stays in the worktree's session dir.
- **Dev cert trust** — the guest generates the ASP.NET dev cert at boot and trusts it in both the system CA bundle (.NET `HttpClient`) and the NSS store `~/.pki/nssdb` (other non-Chromium NSS consumers) — but not Chromium: the cert is a self-signed leaf, and Chromium's builtin verifier won't accept it as a trust anchor via NSS trust settings alone. `shunt-dev playwright` works anyway because the image separately bakes `--allow-insecure-localhost` into playwright-cli's global config, applied to every invocation and scoped to literal `localhost`/`127.0.0.1` origins. A script that imports the `playwright` Node library directly bypasses that config and must pass the same flag itself in its launch options — never `ignoreHTTPSErrors`.

## The `.shunt.app.json` contract (one per repo)

```json
{
  "runner": "node",
  "start": "pnpm dev",
  "workdir": "src/web",
  "frontDoor": [
    { "key": "web", "kind": "http", "listenPort": 7011, "guestPort": 7011, "resource": "web", "tls": true },
    { "key": "db", "kind": "layer4", "listenPort": 5432, "guestPort": 5432, "resource": "postgres" }
  ],
  "mounts": [
    { "host": "~/.microsoft/usersecrets", "guest": "/root/.microsoft/usersecrets", "readOnly": true }
  ],
  "prebakeImages": [
    "postgres:16",
    "mcr.microsoft.com/azure-storage/azurite:3.35.0"
  ],
  "prebakeBuilds": [
    { "image": "example/app-dependency:dev", "context": "containers/dependency", "dockerfile": "containers/dependency/Containerfile", "platform": "linux/arm64", "buildArgs": { "MODE": "dev" } }
  ],
  "dataVolumes": ["postgres-data"],
  "fixedPorts": true
}
```

- The example is valid JSON for a Node app. `runner` is how the app starts: `aspire` keeps gRPC discovery; `dotnet`, `node`, and `custom` use `start` plus a per-route `guestPort` (the in-guest port the app binds). `app add` auto-detects common cases and asks when it can't.
- `frontDoor` maps each service to a stable local port (the host:port you and Entra always hit). `kind` is `http` (web) or `layer4` (raw TCP, e.g. SQL). **HTTP routes serve HTTPS** at the front door using the **.NET dev cert** (run `shunt cert install` once so it's trusted); the proxy reaches the app over TLS with skip-verify. `layer4` routes stay raw TCP.
- **Ports are host == guest.** Set each route's `listenPort` and `guestPort` to the app's actual port. For Aspire, that is the project's launchSettings port. Shunt runs the Aspire AppHost with its launch profile, then bridges each route to the same port on the guest IP. No random bridge ports.
- `mounts` carries per-project host paths into the guest (typically user-secrets so the app's config resolves). Each entry is either a plain path string — `"~/.microsoft/usersecrets"` auto-maps the host home to the guest home (`/root/…`) read-only, `"/abs"` maps to the same path — or the full `{ "host", "guest", "readOnly" }` object for read-write or a different guest path.
- `fixedPorts: true` pins the front door to the exact `listenPort` values (no channel offset) — required for host==guest when the app's config + Entra redirect URIs point at specific ports. Default (omit it) lets the channel offset apply so channels coexist (ports won't match the app then).
- `prebakeImages` is the authoritative registry dependency-image set. Entries must be unique tags: Docker save/load cannot recreate a runnable `repo@digest` alias. `prebakeBuilds` declares local images to build with Apple `container`, including the output tag, context, Dockerfile, platform, and optional build arguments. `warm` refreshes every registry tag and rebuilds every local declaration into immutable per-image exports in a `0700` content-addressed cache directory. Lifecycle commands assure the cache, load only missing or changed refs, then update the marker. Sidings never pull live, so an undeclared or unavailable image fails startup. Apple `container` is the only host runtime requirement because Docker runs inside guests; Docker Desktop and OrbStack are not dependencies. Publication automatically collects unreachable content; `warm gc --dry-run` previews that collector, and `warm gc` runs it explicitly while retaining current, previous, and leased generations.
- `dataVolumes` lists unique Docker named volumes the application uses. The initial source is empty. `data promote` installs a quiesced siding's complete set as the next canonical generation for future `new` and `reapply --fresh-data`; already-created siding copies remain unchanged, while plain `reapply` preserves the siding copy. `data rollback` swaps back one generation. If a promoted generation is bad, roll it back before rebuilding sidings from the recovered generation. Once a baseline is initialized, its volume set is immutable: update the contract only after deliberately removing the old baseline, then register the app and initialize a new baseline.
- `memory`/`cpus` cap each siding guest (e.g. `"memory": "12g"`) — heavy stacks (SQL + several services) need headroom; omit to use the `shunt config` default (`4g`/`4`). Changing them needs `shunt reapply [siding]` (caps are fixed at guest creation).
- `healthPort`/`healthPath` set the endpoint hit (from inside the guest) to decide whether a siding is genuinely `running` vs merely `idle` (booted, not serving) — used by both the **dashboard** status and by **`up`** (which rebuilds a running-but-unhealthy app). Omit `healthPort` to default to the Aspire dashboard's home page (up whenever the AppHost is); **but that default only detects a fully-dead AppHost** — if the AppHost is up but its child projects all crashed, the dashboard page still answers, so point `healthPort` at a real app route (e.g. `"healthPort": 8080, "healthPath": "/healthz"`) to catch a half-dead stack. `healthPath` defaults to `/`.
- `disableCache: true` makes the front door send `Cache-Control: no-store` on every HTTP response for this app — the whole environment serves uncached. Use it for Blazor/SPA apps that boot **stale** after you switch sidings on the shared front-door port (the browser otherwise reuses the previous siding's cached boot manifest). Applies on `app add` (front-door config, not a guest cap — no `reapply` needed).
- shunt has no app-specific logic; this file is the only per-repo config.
