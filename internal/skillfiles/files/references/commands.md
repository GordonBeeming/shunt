# shunt command reference

This installed reference is scoped to `{{shunt-command}}`; every command below uses that channel's binary.

{{shunt-channel-onboarding}}

| Command | What it does |
|---|---|
| `{{shunt-command}} active [--json]` | Does the current Git repository, nested directory, or siding worktree have durable Shunt state? Lists sidings with `live`, `appRunning`, `guestRunning`, and their `src` edit paths. JSON keeps `active` as the compatibility signal for a registered app and adds `managed` for any durable Shunt state: `managed: true, active: false, registered: false` means worktree-only state that needs `app add` before a guest. Plain mode exits non-zero only when no Shunt state exists. |
| `{{shunt-command}} base` / `base set <siding>` | Show the source base, or pin a siding's committed HEAD as the source for default `new`. A dirty siding may be selected, but default `new` stays blocked until it is clean. With zero sidings, `base` shows the saved commit. |
| `{{shunt-command}} ls [-a] [--json]` | List sidings for the current project, or every registered project with `--all`. `--json` remains a top-level array for existing consumers; each app adds `schemaVersion: 2`, and each siding adds persisted `phase` plus observed `runtime`/`runtimeDetail`. Legacy `status` (`live`/`up`/`idle`/`stopped`) and `guest` (`running`/`stopped`) stay compatible. There is no host row. |
| `{{shunt-command}} status [--fix] [--json]` | Report channel machinery, bounded runtime state/detail, and per-app front-door drift. An app with a durable removal journal reports its operation ID, siding, stage, generation, start/age, and the exact `{{shunt-command}} rm <siding>` resume command. `--fix` re-points a live route whose saved guest IP changed after a restart. |
| `{{shunt-command}} new <name> [--branch <ref>\|--from <branch>]` | Create only a managed branch and worktree. In an unregistered Git repository, this lazily creates the minimal persistent project and control-repository state; it does not read `.shunt.app.json` or publish a registry entry. No data, output directory, image load, guest, or application is created. The first siding becomes the source base. Default source is the clean base siding's committed HEAD, or its pinned commit when zero sidings remain. `--branch` deliberately chooses another start ref; `--from` fetches and continues an existing remote branch. |
| `{{shunt-command}} up [name] [--no-bridge] [--switch]` | Lazily grow a worktree through data and guest phases, create `out`, assure and load declared dependency images, and start the app. A worktree-only project must first add `.shunt.app.json` and run `{{shunt-command}} app add`. By default `up` bridges without moving the front door. `--no-bridge` starts privately; `--switch` deliberately goes live. A parked siding reuses its data/output and recreates only the guest. |
| `{{shunt-command}} warm [--from <siding>]` | Refresh every configured `prebakeImages` registry tag and rebuild every `prebakeBuilds` image, then atomically publish immutable per-image cache generations. `--from <siding>` captures a running guest's Docker store instead, bounded by the configured cache budget. A failed automatic collection warns without undoing the published generation. |
| `{{shunt-command}} warm gc [--dry-run] [--max-bytes N]` | Run the collector that also follows every successful cache publication. It mark/sweeps unreachable generations, exports, and blobs. Current, previous, and actively leased generations are protected. The default budget is 100 GiB; protected data is never removed merely to meet it. Set `SHUNT_CACHE_MAX_BYTES` to change the default budget. |
| `{{shunt-command}} data promote [siding] [-f]` | Promote the siding's complete declared-volume set. Source resolution is an explicit arg, cwd siding, live siding, then picker. The application and volume consumers are stopped and verified, data is durably committed, and the previous idle/running/live state is restored. A post-commit cleanup problem is printed as a warning and must not be retried as though publication failed. |
| `{{shunt-command}} data rollback [-f]` | Durably swap the current and immediately previous complete data baseline. A post-commit cleanup problem warns without turning the already-completed mutation into a retryable failure. |
| `{{shunt-command}} restart [name]` | Rebuild only the app process while keeping the materialized guest, Docker daemon, dependencies, and data running. Worktree/data/parked sidings must be grown with `up` first. |
| `{{shunt-command}} logs [name] [-n N]` | Print build, startup, and crash output from a siding's guest. Use it to diagnose a failed `up`. |
| `{{shunt-command}} git [args]` | Run **any** git command in the siding's worktree on the **host** (git doesn't resolve inside the guest). Args pass straight through to `git -C <worktree> <args>`; signs with your usual key, acts on the siding's `shunt/<name>` branch. Beyond `commit`/`push` this is the full surface for resolving a `sync` conflict — `status`, `diff`, `add`, `restore`, `rebase --continue`/`--abort`, `merge --abort`. Siding taken from cwd or the live one. |
| `{{shunt-command}} sync [name] [--all] [--rebase] [--from <branch>]` | Pull the latest **default branch** (main, auto-detected from `origin/HEAD`) into a siding: `fetch origin` then **merge** it into the siding's `shunt/<name>` branch — a merge that picks up the latest code **without rewriting history** (fast-forwards when the siding has no local commits, else a merge commit; the safe default). `--rebase` rebases onto it instead (rewrites the branch — `git push --force-with-lease` after); `--all` syncs every siding (continues past conflicts, prints a summary); `--from <branch>` syncs from a branch other than the default. On conflicts it stops and lists the files — resolve them in the worktree with `{{shunt-command}} git add …` + `{{shunt-command}} git commit` (merge) or `{{shunt-command}} git rebase --continue` (`--rebase`). Siding taken from the name arg, else cwd, else the live one. |
| `{{shunt-command}} run [siding] [command...]` | Run a command inside a materialized siding guest from the app workdir. Resolution is cwd siding, explicit leading siding name, then live siding. Worktree/data/parked sidings need `up` first. |
| `{{shunt-command}} playwright [siding] [args...]` | Execute `playwright-cli` inside a running guest. Its app URL is the guest's own `https://localhost:<port>`. Sessions persist; auto-named output for sessions opened through this command lands in `<siding>/out/playwright`. |
| `{{shunt-command}} cd [name]` | Print a siding worktree path for `cd "$({{shunt-command}} cd <name>)"`. Resolution is explicit name, cwd siding, then live siding. `host` is rejected because it is not a work target. |
| `{{shunt-command}} switch [name]` | Repoint every stable front-door route at a materialized siding as one operation. It never creates a guest or starts the app; run `up` first. Always confirm before switching because the shared front door can be in use elsewhere. |
| `{{shunt-command}} dashboard [--install]` | Open the hostless dashboard. It shows the base siding, persisted `worktree`/`data`/`guest`/`parked` phase, and observed `running`/`stopped`/`missing`/`runtime-unavailable` state separately. Start shares the lazy `up` path; Park removes a non-live guest after confirmation; Switch and Stop apply only to guests. Mutations require loopback Host, exact same-origin Origin, a per-process CSRF token, JSON, and a bounded single request body. |
| `{{shunt-command}} kill [name]` | Stop a materialized guest but retain it, its worktree, data, and output. If a graceful stop wedges, Shunt force-removes only the guest and tells you to run `up`; other failures fail closed. |
| `{{shunt-command}} park [name]` | Remove a non-live guest while retaining the worktree, data, and output. The next `up` recreates the guest from those durable assets. |
| `{{shunt-command}} rm [name] [-f\|--force] [--next-base <siding>]` | Permanently remove one siding. Dirty/unique work and a live target are protected unless explicitly confirmed/forced. Removing the current base with survivors requires a successor. Removing the final siding pins its commit and promotes a complete materialized volume set as the durable baseline; a worktree-only final siding preserves the existing baseline. |
| `{{shunt-command}} cleanup [-f\|--force] [--next-base <siding>]` | Select and permanently remove several sidings with the same work/live/base safeguards as `rm`. The current base is removed last. Interactive cleanup prompts for a surviving successor; non-interactive use must pass `--next-base`. |
| `{{shunt-command}} space [--all] [--json]` | Report physical filesystem capacity separately from logical source/generated/output/data/protected-baseline scans and Git evidence. The control store and image cache are named managed rows; legacy/unknown on-disk entries are unclassified with ownership/reclaimability unverified. Clone-overlapping logical totals are never called reclaimable. Apple-container reclaimability comes only from official `container system df --format json`; an unavailable service is reported as unobserved and is not started. |
| `{{shunt-command}} trim <siding> [--dry-run] [--yes\|-y]` | Preview or delete only exact allow-listed generated directories that Git confirms are ignored and untracked. It refuses symlinks and protected paths. After confirmation it locks the siding, checks the preview is unchanged, quarantines the complete set on the same filesystem, checks Git again, and restores the set if validation fails before deletion. Logical candidates remain separate from the actual filesystem free-space delta. |
| `{{shunt-command}} reapply [name] [--fresh-data]` | Recreate a materialized guest from saved settings while keeping its worktree and data. `--fresh-data` discards that siding's volume changes and clones the selected baseline again. Run `app add` first after changing shared saved settings, then `up`. |
| `{{shunt-command}} app add` | Read `.shunt.app.json`, register or refresh the app, create/verify the self-contained hidden `.control.git`, and pin the source seed. If `new` already created worktree-only state, registration enriches it in place and preserves every siding. The original checkout remains a registration/legacy source reference, not a runtime host. Re-run from the registration checkout after changing the shared contract; a siding's own front-door contract is read by `up`/`switch`. |
| `{{shunt-command}} app switch <app>` | Make `<app>` active on its fixed front-door ports. A conflicting app temporarily releases its front-door binding without stopping its siding or changing that siding's materialization phase; this is distinct from `{{shunt-command}} park <siding>`. |
| `{{shunt-command}} init` | One-time machine setup: starts Apple container, builds Caddy + the base image, exports the development certificate, and starts the proxy. |
| `{{shunt-command}} cert install` | Reload the host's dotnet dev cert into Caddy after trust, rotation, or regeneration (front door serves HTTPS with the cert you already trust — no extra CA). |
| `{{shunt-command}} config <branchPrefix\|memory\|cpus> [value]` | Get/set per-channel defaults. `branchPrefix` affects future siding branches; `memory` and `cpus` affect future guests. Existing materialized guests need `reapply` + `up`; a worktree-only siding simply uses the current settings on its first `up`. |
| `{{shunt-command}} skill install [agent...] [--all]` | Install the binary's embedded, source-of-truth skill into detected Claude Code, Codex, and OpenCode installations, or explicitly named targets. |
| `{{shunt-command}} version` | Print the build channel, `version=<build-version>`, and its resolved binary, Caddy admin port, port offset, and guest-name prefix. |

## Persisted state compatibility

Legacy projects load from `state.json` with safe in-memory defaults. Legacy worktrees keep their original owner and pre-phase sidings project as materialized guests. One existing siding becomes the unambiguous base; with several, interactive source operations ask and non-interactive use must run `base set <siding>`. The next state publication atomically renames `state-v2.json` into place; once present, v2 is authoritative and later legacy-file writes are ignored. Unsupported future versions fail closed instead of being rewritten. A removal journal is project-exclusive and resumable, and mutating source/lifecycle/data/Git/trim paths reload it after acquiring their operation lock.

## Guest layout

- **`/out`** — every siding's guest gets a standing bind mount here, backed by `<siding>/out` on the host: outside the worktree and never committed, it's the landing spot for ad hoc logs or generated config you want to inspect from the host. `{{shunt-command}} playwright` (above) auto-names its output under `/out/playwright` (`<siding>/out/playwright` on the host) via `PLAYWRIGHT_MCP_OUTPUT_DIR`, injected automatically; an explicit `--filename` bypasses that and resolves relative to the guest's cwd (the worktree) instead, so pass an explicit `/out/...` path if you want a named file to land there too. That env var is only set when the browser session **opens**, and the redirect it picks sticks for the session's whole life: a session opened via a manual `{{shunt-command}} run <siding> playwright-cli open …` never gets it, so its auto-named output — video included — stays in the worktree's `.playwright-cli/` for as long as that session runs, even if later calls on it switch to `{{shunt-command}} playwright`. Open sessions through `{{shunt-command}} playwright`; treat `{{shunt-command}} run … playwright-cli` as a fallback whose output stays in the worktree's session dir.
- **Dev cert trust** — the guest generates the ASP.NET dev cert at boot and trusts it in both the system CA bundle (.NET `HttpClient`) and the NSS store `~/.pki/nssdb` (other non-Chromium NSS consumers) — but not Chromium: the cert is a self-signed leaf, and Chromium's builtin verifier won't accept it as a trust anchor via NSS trust settings alone. `{{shunt-command}} playwright` works anyway because the image separately bakes `--allow-insecure-localhost` into playwright-cli's global config, applied to every invocation and scoped to literal `localhost`/`127.0.0.1` origins. A script that imports the `playwright` Node library directly bypasses that config and must pass the same flag itself in its launch options — never `ignoreHTTPSErrors`.

## The `.shunt.app.json` contract (one per repo)

```json
{
  "runner": "node",
  "start": "pnpm dev",
  "workdir": "src/web",
  "frontDoor": [
    { "key": "web", "kind": "http", "listenPort": 7011, "guestPort": 7011, "resource": "web", "tls": true },
    { "key": "db", "kind": "layer4", "listenPort": 5432, "guestPort": 5432, "resource": "postgres" }
  ],
  "mounts": [
    { "host": "~/.microsoft/usersecrets", "guest": "/root/.microsoft/usersecrets", "readOnly": true }
  ],
  "prebakeImages": [
    "postgres:16",
    "mcr.microsoft.com/azure-storage/azurite:3.35.0"
  ],
  "prebakeBuilds": [
    { "image": "example/app-dependency:dev", "context": "containers/dependency", "dockerfile": "containers/dependency/Containerfile", "platform": "linux/arm64", "buildArgs": { "MODE": "dev" } }
  ],
  "dataVolumes": ["postgres-data"],
  "fixedPorts": true
}
```

- The example is valid JSON for a Node app. `runner` is how the app starts: `aspire` keeps gRPC discovery; `dotnet`, `node`, and `custom` use `start` plus a per-route `guestPort` (the in-guest port the app binds). `app add` auto-detects common cases and asks when it can't.
- `frontDoor` maps each service to a stable local port (the host:port you and Entra always hit). `kind` is `http` (web) or `layer4` (raw TCP, e.g. SQL). **HTTP routes serve HTTPS** at the front door using the **.NET dev cert** loaded by `init`; trust it with `dotnet dev-certs https --trust`, then reload it with `cert install` only after trust, rotation, or regeneration. The proxy reaches the app over TLS with skip-verify. `layer4` routes stay raw TCP.
- **Ports are host == guest.** Set each route's `listenPort` and `guestPort` to the app's actual port. For Aspire, that is the project's launchSettings port. Shunt runs the Aspire AppHost with its launch profile, then bridges each route to the same port on the guest IP. No random bridge ports.
- `mounts` carries per-project host paths into the guest (typically user-secrets so the app's config resolves). Each entry is either a plain path string — `"~/.microsoft/usersecrets"` auto-maps the host home to the guest home (`/root/…`) read-only, `"/abs"` maps to the same path — or the full `{ "host", "guest", "readOnly" }` object for read-write or a different guest path. Keep user-secrets mounts read-only: every worktree with the same `<UserSecretsId>` shares the host store. Read-only protects it from guest processes, but host-side `dotnet user-secrets` commands run in a siding worktree still change the values seen by the registration checkout and all sidings.
- `fixedPorts: true` pins the front door to the exact `listenPort` values (no channel offset) — required for host==guest when the app's config + Entra redirect URIs point at specific ports. Default (omit it) lets the channel offset apply so channels coexist (ports won't match the app then).
- `prebakeImages` is the authoritative registry dependency-image set. Entries must be unique tags: Docker save/load cannot recreate a runnable `repo@digest` alias. `prebakeBuilds` declares local images to build with Apple `container`, including the output tag, context, Dockerfile, platform, and optional build arguments. `warm` refreshes every registry tag and rebuilds every local declaration into immutable per-image exports in a `0700` content-addressed cache directory. Lifecycle commands assure the cache, load only missing or changed refs, then update the marker. Sidings never pull live, so an undeclared or unavailable image fails startup. Apple `container` is the only host runtime requirement because Docker runs inside guests; Docker Desktop and OrbStack are not dependencies. Publication automatically collects unreachable content; `warm gc --dry-run` previews that collector, and `warm gc` runs it explicitly while retaining current, previous, and leased generations.
- `dataVolumes` lists unique Docker named volumes the application uses. The initial source is empty. `new` is worktree-only and never touches data. `data promote` installs a quiesced siding's complete set as the canonical generation for future first `up` materializations and `reapply --fresh-data`; already-materialized siding copies remain unchanged, while plain `reapply` preserves the siding copy. `data rollback` swaps back one generation. If a promoted generation is bad, roll it back before rebuilding sidings from the recovered generation. Once a baseline is initialized, its volume set is immutable: update the contract only after deliberately removing the old baseline, then register the app and initialize a new baseline.
- `memory`/`cpus` cap each siding guest (e.g. `"memory": "12g"`) — heavy stacks (SQL + several services) need headroom; omit to use the `{{shunt-command}} config` default (`4g`/`4`). Changing them needs `{{shunt-command}} reapply [siding]` (caps are fixed at guest creation).
- `healthPort`/`healthPath` set the endpoint hit (from inside the guest) to decide whether a siding is genuinely `running` vs merely `idle` (booted, not serving) — used by both the **dashboard** status and by **`up`** (which rebuilds a running-but-unhealthy app). Omit `healthPort` to default to the Aspire dashboard's home page (up whenever the AppHost is); **but that default only detects a fully-dead AppHost** — if the AppHost is up but its child projects all crashed, the dashboard page still answers, so point `healthPort` at a real app route (e.g. `"healthPort": 8080, "healthPath": "/healthz"`) to catch a half-dead stack. `healthPath` defaults to `/`.
- `disableCache: true` makes the front door send `Cache-Control: no-store` on every HTTP response for this app — the whole environment serves uncached. Use it for Blazor/SPA apps that boot **stale** after you switch sidings on the shared front-door port (the browser otherwise reuses the previous siding's cached boot manifest). Applies on `app add` (front-door config, not a guest cap — no `reapply` needed).
- shunt has no app-specific logic; this file is the only per-repo config.
